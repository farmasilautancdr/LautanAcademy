- G. Active sessions + force-logout — DONE 2026-08-11. Real architecture change: auth was fully stateless JWT with zero session tracking before this. New `sessions` table (backend, bigserial id) — one row per staff/manager login only, **Master's own tokens excluded/untracked by design** (decided during brainstorming: too few Master accounts to justify self-lockout risk). `issueToken()` now inserts a session row and embeds its id as a `sid` string claim in the JWT (kept a string everywhere — cache Set, revoke-route params — to avoid repeating the logged `standard_questions.id` string/number bug). `requireAuth` checks `sid` against a new in-memory revocation cache (`services/sessionRevocationCache.js`) instead of a live DB query per request — decided during brainstorming as the lighter-weight alternative to a per-request DB check; refreshed by a ~25s background poller (also prunes sessions older than 30 days, no separate cron mechanism exists), with the revoke route also writing directly into the cache so force-logout is instant for the process handling it, confirmed via curl (immediate 401 on the very next request, no wait). New `routes/masterSessions.js`: `GET /master/sessions/search` (filters: scopeType exact, scopeKey partial-match, activeOnly) and `POST /master/sessions/revoke` (`{ids: [...]}` bulk array — deliberately reuses the same ids-array convention every other Master purge route already uses, covering both single and multi-select force-logout with one endpoint instead of a separate filter-based bulk route). Frontend: `MasterActiveSessions.vue` wired into the `sessions` tab, same search-table pattern as Audit Log, single-row revoke uses a lightweight native `confirm()` (reversible — just log back in), bulk revoke reuses `MasterDeleteConfirmModal.vue`'s typed-DELETE pattern. Verified: full curl round-trip (fresh staff login → session row created with correct `sid` claim → Master search finds it → revoke → **immediate** 401 on the already-issued staff token, proving the direct-cache-write path, not just eventual poll consistency → Master's own token unaffected throughout → audit_log entry confirmed correct), multi-session bulk revoke, empty-ids 400 guard, 401/403 auth gating, `npm run build` clean, EN/MS key-parity script clean, user's live browser click-through confirmed force-logout actually logs out the other tab in real time. **BM strings not independently re-confirmed live this time** — user said "bm string not too important" for this panel; keys exist and pass the parity script (structurally correct, same caveat pattern as Subsystem F's BM gap) but weren't eyeballed rendering. **Real finding during migration**: this Supabase project's `auth` schema already has its own unrelated `sessions` table (Supabase Auth internals) — an unscoped `information_schema` query on `'sessions'` double-matches both; our `public.sessions` was confirmed clean and correctly scoped, but this is now flagged in `sql/schema.sql`'s comment for future reference. **Two operational incidents during this session, both recovered, neither is a Subsystem G code bug**: (1) ran `taskkill /F /IM node.exe` to restart the backend, which kills *every* Node process system-wide, not just the target — killed an unrelated already-running frontend dev server (37 processes total) as collateral; going forward, target the specific PID/port, never a blanket image-name kill.
