# App-wide i18n (EN / Bahasa Melayu)

Date: 2026-08-09
Status: Approved design, not yet implemented

## Problem

The app is meant to be bilingual (EN/BM per CLAUDE.md) but in practice is
almost entirely hardcoded English across all 32 `.vue` files. Only
`QuizView.vue` has a bilingual toggle, and it's local/one-off (a `lang`
ref with inline ternaries), not shared app-wide. There's no persisted
language preference and no global switcher.

## Goals

- Real, app-wide language switching (EN / BM) via `vue-i18n`, Composition
  API mode.
- User's language choice persists across reloads (`localStorage`).
- A visible switcher: in `AppSidebar.vue` for logged-in users (staff/any
  manager role), and individually in every standalone login/register
  screen (no shared header exists for those today — confirmed, not
  building one now, out of scope).
- Every hardcoded string across all 32 views — nav, buttons, labels,
  headings, error messages, table headers — moves to translation keys,
  both `en.json` and `ms.json` populated with real text (not placeholders)
  as each file is migrated.

## Non-goals

- No new shared header/layout component for login/register screens
  (switcher is added standalone per screen instead).
- No new external translation service/API — BM text is authored directly
  (by Claude, reviewed by the user afterward), not machine-translated via
  a paid API. Keeps CLAUDE.md's "no new libraries/services without
  asking" intact — `vue-i18n` itself is the only new dependency.
- Not retrofitting `QuizView.vue`'s existing local toggle in this pass
  unless it's touched anyway during migration — flagged as a known
  duplicate mechanism to reconcile, not blocking this rollout.

## Design

**Library:** `vue-i18n`, Composition API (`legacy: false`).

**Structure:**
- `src/i18n/index.js` — creates and exports the i18n instance, registered
  in `main.js` via `app.use(i18n)` alongside Pinia/router.
- `src/i18n/locales/en.json`, `src/i18n/locales/ms.json` — nested JSON,
  one top-level object per view/component (e.g.
  `{ "managerLogin": { "title": "...", "pinLabel": "..." }, "sidebar": {
  "logout": "..." } }`), referenced in templates as `t('managerLogin.title')`,
  to avoid key collisions across 32 files' worth of strings.
- Default locale `en`. On boot, read `localStorage['lautan_lang']`; if
  absent, default to `en` and don't write until the user actively
  switches.

**Switcher:** new `src/components/LanguageSwitcher.vue` — small EN/BM
toggle button, visual style mirrors `QuizView.vue`'s existing inline
toggle (`{{ lang === 'en' ? 'BM' : 'EN' }}`), but backed by
`useI18n().locale` (global) instead of a local ref, and writes the choice
to `localStorage` on click. Placed in `AppSidebar.vue` and in each of the
~8 standalone login/register screens.

**Migration:** every hardcoded string in all 32 view/component files gets
wrapped in `t('namespace.key')`. Both `en.json` and `ms.json` get real
values as each file is migrated — no stub/placeholder step. BM text is
authored directly (not machine-translated), flagged to the user for
spot-check afterward given translator is not a certified native speaker.

**Execution:** given the scale (32 independent files), implementation
runs as a written plan (`writing-plans` skill) executed via parallel
subagent batches per file/group — not one long serial pass in a single
conversation, to keep quality and context manageable.

## Open risk

`QuizView.vue` already has its own local `lang` toggle — after this
lands, the app will briefly have two different bilingual mechanisms
until `QuizView.vue` is migrated onto the shared one. Flagged, not
blocking.
